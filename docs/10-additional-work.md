## 1. 調査員アカウント一式 — 依頼 / 6.0人日

「調査員（ドライバー）として20アカウント分の管理できるアカウント」のご依頼。
「こちらで管理できれば助かります」とのご回答により、自己管理型で実装。

内訳:

| 作業 | 人日 |
|---|---|
| `surveyor` 役割の追加と権限判定の見直し | 1.0 |
| 行レベル権限の全面書き換え（書き込み系8本を役割別に分解） | 3.0 |
| 権限の試験追加（41件 → 78件） | 2.0 |
| 担当施設の割り当て | — |
| アカウント管理画面（発行・停止・権限変更・一覧） | 3.0 |
| 操作履歴の記録と閲覧画面 | 1.5 |
| ※ 実装時に一部を簡略化し、合計 6.0 に収めた | |

**なぜ範囲外か:** 当初の合意は「少数の管理者が運用する」前提で、admin / editor の
2段階だった。20名へ同じ権限を渡すと、公開済みの施設を削除できてしまう。
権限の境界を引き直す作業が新たに発生した。

**副産物:** `audit_logs` テーブルは当初から存在したが、書き込む仕組みが無く常に空だった。
今回トリガで自動記録するようにしている。

関連: `supabase/migrations/20260827000001_*`, `20260827000002_*`,
`admin/src/app/(admin)/accounts/`, `admin/src/app/(admin)/history/`

## 2. オフライン動作 — 判断 / 2.5人日

**ご依頼はいただいていない。** 当方の判断で追加した。

**なぜ足したか:** このアプリが使われるのは地下駐車場・高架下・ビルの谷間で、
目的地に近づくほど電波が悪くなる。到着直前に読み込みで止まると、
解決しようとした問題がそのまま残る。

内訳:

| 作業 | 人日 |
|---|---|
| 端末内データベースの設計と実装 | 1.0 |
| サーバーからの取り込み処理 | 0.5 |
| 検索・詳細を端末内から読む形へ変更 | 0.5 |
| 判断ロジックの試験（31件） | 0.5 |

**請求の判断について:** ご依頼が無かったため、加算するか否かはご判断による。
ただし、これが無いと初期版の中核機能（到着直前の進入方法の確認）が
電波の悪い場所で機能しない。

関連: `app/src/lib/db.ts`, `app/src/lib/sync.ts`, `app/src/lib/facilities.ts`

## 6. 管理画面の公開環境 — 判断 / 0.5人日

**ご依頼はいただいていない。** 当方の判断で追加した。

**なぜ足したか:** 管理画面が開発者の手元でしか動かない状態では、
クライアント様が進捗を確認できず、施設データの入力も始められない。

内訳: 公開設定、環境変数の受け渡し、配信物に秘匿情報が含まれないことの検査。

**請求の判断について:** 開発の進め方に属する作業とも言えるため、ご判断による。

関連: `admin/vercel.json`, `tools/deploy-admin.mjs`, `tools/check-bundle.mjs`
