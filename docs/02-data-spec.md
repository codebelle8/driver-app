# データ項目定義書

作成日: 2026-08-07 / 対象: 初期版 (MVP)
対応スキーマ: [`db/migrations/0001_initial_schema.sql`](../db/migrations/0001_initial_schema.sql)

---

## 1. データ構造の考え方

```
カテゴリ (categories)
  └─ 施設 (facilities)                     … グランドホテル汐留
       ├─ 車寄せ・エントランス (entry_points)  … 正面車寄せ / 宴会場エントランス
       │    ├─ 注意事項 (cautions)            … 17〜20時は送迎バスで通過不可
       │    └─ 写真・案内図 (photos)          … 進入路 / 車寄せ / 夜間 / 案内図
       └─ 写真 (photos)                       … 施設外観
```

**1施設に複数の進入口がある**ことがこのアプリの前提。同じ建物でも「正面車寄せ」と
「宴会場エントランス」では進入路も停車位置も注意事項も異なる。ドライバーが本当に
知りたいのは施設ではなく**進入口**の情報であり、データ構造もそれに合わせている。

| code | 表示名 | 接頭辞 | 表示順 |
|---|---|---|---|
| `hotel` | ホテル | `HTL` | 10 |
| `residence` | **レジデンス** | `RSD` | 20 |
| `commercial` | 商業施設 | `CML` | 30 |
| `office` | オフィスビル | `OFC` | 40 |
| `hospital` | 病院 | `HSP` | 50 |
| `station` | 駅・空港 | `STN` | 60 |

> **2026-08-07 更新**: 上野様より「まずは主要ホテル、有名レジデンス等を進めたい」との
> ご意向があり、**レジデンスをカテゴリに追加**し、ホテルに次ぐ表示順とした。
>
> レジデンス（タワーマンション・高級賃貸）は、車寄せがゲート内にあり、
> 住民用と来客用でエントランスが分かれ、コンシェルジュ対応の有無で停車位置が
> 変わるなど、本アプリが解決したい課題が最も濃く出る施設種別である。
> `entry_points.kind` に `service`（関係者用）を用意しているのはこの想定による。

## 3. 施設 (facilities)

| 項目 | 列名 | 型 | 必須 | 内容 |
|---|---|---|---|---|
| 施設コード | `code` | text | ● | `HTL-0001` 形式。**写真ファイル名と対応**。採番は当方 |
| 施設名 | `name` | text | ● | 正式名称 |
| 施設名（かな） | `name_kana` | text | ● | 検索用。ひらがな/カタカナどちらでも可 |
| 別名・略称 | `aliases` | text[] | | ドライバーが口頭で言う呼び方。`;` 区切りで入力 |
| カテゴリ | `category_id` | uuid | ● | 上表のいずれか |
| 郵便番号 | `postal_code` | text | | |
| 都道府県 | `prefecture` | text | ● | |
| 市区町村 | `city` | text | | |
| 住所 | `address_line` | text | ● | 町名・番地・建物名 |
| 施設概要 | `summary` | text | | 2〜3行 |
| 代表座標 | `lat` / `lng` | float | | 地図初期表示用。**ナビ目的地には使わない** |
| 公開状態 | `status` | enum | ● | `draft` / `published` / `archived` |
| 管理メモ | `note_internal` | text | | アプリには表示しない |

### 公開状態について

データは段階的に入稿されるため、**未完成の施設は `draft` のまま保持**し、
揃ったものだけ `published` にする。アプリからは `published` の施設しか見えない。

公開してよいかは `validate_facility_for_publish()` が機械的に判定する。

| 判定内容 | 結果 |
|---|---|
| 施設名・かな・住所が未入力 | 公開不可 |
| 有効な進入口が0件 | 公開不可 |
| ナビ投入座標が無い進入口がある | 公開不可 |
| 進入方法の説明が無い進入口がある | 公開不可 |
| 写真が1枚も無い進入口がある | 公開不可 |
| 仮画像が残っている | **警告のみ**（公開は可能） |

仮画像を警告どまりにしているのは、**写真の入稿を待たずに公開できる**ようにするため。
文章と座標さえ正しければ、ドライバーにとっては既に十分な価値がある。

## 4. 車寄せ・エントランス (entry_points) — 中核データ

| 項目 | 列名 | 型 | 必須 | 内容 |
|---|---|---|---|---|
| 記号 | `code` | text | ● | `A` `B` `C`…。施設内で一意。**写真ファイル名と対応** |
| 区分 | `kind` | enum | ● | 下表参照 |
| 名称 | `name` | text | ● | 「正面車寄せ（メインポーチ）」 |
| 進入方法の説明 | `approach_text` | text | ●※ | 「海岸通り側から進入し、スロープを上がって2階レベルの車寄せへ」 |
| 進入元の道路・方向 | `approach_from` | text | | 「海岸通り（北行き）から」 |
| **ナビ投入座標** | `nav_lat` / `nav_lng` | float | ●※ | **進入レーン上**の地点 |
| 停車位置座標 | `dropoff_lat` / `dropoff_lng` | float | | 実際に停車する位置 |
| 高さ制限 | `height_limit_cm` | int | | ハイヤー・ワゴンの可否判断 |
| 屋根の有無 | `is_roofed` | bool | | |
| 24時間利用可 | `is_24h` | bool | | |
| 有効 | `is_active` | bool | ● | 一時閉鎖中の進入口を隠す |

※ = 公開時に必須（下書き段階では空でよい）

### 区分 (`kind`)

| 値 | 表示 | 用途 |
|---|---|---|
| `dropoff` | 車寄せ | 乗降のための停車スペース |
| `entrance` | エントランス | 建物入口（車寄せと別位置の場合） |
| `parking_entrance` | 駐車場入口 | |
| `bus_stop` | バス乗降場 | シャトルバス乗降場など |
| `service` | 関係者用 | レジデンスの荷捌き口・業者用入口 |

### ナビ投入座標と停車位置を分けている理由

地図アプリに建物の代表地点を渡すと、**建物の反対側から到着する経路**が案内される
ことがある。一方通行や中央分離帯があると、そこから車寄せに入り直すのに数分かかる。

そこで、ナビに渡す座標は**進入レーン上の地点**とし、停車位置とは別に保持する。
どちらの座標も持っておくことで、画面上では停車位置を示しつつ、ナビには進入地点を
渡す、という使い分けができる。

## 5. 注意事項 (cautions)

| 項目 | 列名 | 型 | 必須 | 内容 |
|---|---|---|---|---|
| 本文 | `body` | text | ● | 「17〜20時は送迎バスが停車するため手前のレーンは通過できません」 |
| 重要度 | `severity` | enum | ● | `info` / `warn` / `critical` |
| 開始時刻 | `time_from` | time | | 空欄なら常時適用 |
| 終了時刻 | `time_to` | time | | `22:00`〜`05:00` のような日跨ぎも可 |
| 適用曜日 | `weekdays` | int[] | | ISO 準拠 1=月 … 7=日。空なら全曜日 |

**時間帯を文章に埋め込まず、独立した項目として持つ**ことで、アプリ側は
「今この瞬間に該当する注意事項」だけを強調表示できる。運転中に読む情報量を
減らすことが安全につながるため、この構造化には実用的な意味がある。

## 6. 写真・進入案内図 (photos)

| 項目 | 列名 | 型 | 必須 | 内容 |
|---|---|---|---|---|
| 種類 | `kind` | enum | ● | 下表参照 |
| 保存パス | `storage_path` | text | ● | Supabase Storage 上のパス |
| キャプション | `caption` | text | | 「正面車寄せ（夜間）」 |
| 撮影日 | `taken_on` | date | | 改修の追跡に使う |
| 仮画像 | `is_placeholder` | bool | ● | 実写真の入稿待ちを抽出するため |
| 表示順 | `sort_order` | int | ● | |

### 種類 (`kind`)

| 値 | 表示 |
|---|---|
| `approach` | 進入路 |
| `dropoff` | 車寄せ |
| `entrance` | エントランス |
| `night` | 夜間 |
| `diagram` | 進入案内図（1進入口につき1枚） |
| `exterior` | 施設外観 |
| `other` | その他 |

### ファイル命名規則

```
{施設コード}_{進入口記号}_{種類}_{連番}.{拡張子}

例:
  HTL-0001_A_dropoff_01.jpg     グランドホテル汐留 / 正面車寄せ / 車寄せ写真 1枚目
  HTL-0001_A_night_01.jpg       同 / 夜間写真
  HTL-0001_A_diagram_01.png     同 / 進入案内図
  HTL-0001_B_approach_01.jpg    同 / 宴会場エントランス / 進入路写真
  RSD-0003_exterior_01.jpg      レジデンス / 施設外観（進入口記号なし）
```

- 種類は上表の `kind` の値をそのまま使う
- 連番は 2桁ゼロ埋め
- 拡張子は `.jpg` `.png` のいずれか。案内図は `.png` を推奨（線と文字が潰れないため）

### 推奨仕様

| 項目 | 推奨 |
|---|---|
| 写真の解像度 | 長辺 1600px 以上（アプリ側で自動圧縮する） |
| 案内図 | PNG。PDF でご提供の場合は当方で PNG に変換 |
| 1進入口あたりの枚数 | 3〜5枚（進入路・車寄せ・エントランス・夜間） |

配信時はサーバー側で **サムネイル 400px / 詳細 1200px の WebP** に変換し、
CDN 経由で配信する。原本は差し替え・再生成のために保管する。

## 7. 仮データ（プレースホルダー）運用

実データの入稿を待たずに全画面を実装するため、以下の運用とする。

| 対象 | 仮データの扱い |
|---|---|
| 写真・案内図 | 「準備中」を示すダミー画像。`is_placeholder = true` |
| 施設名・住所・説明文 | サンプル値を投入。`status = draft` のまま |
| 座標 | 未設定のまま可（公開時に必須チェックが働く） |

**差し替えは管理画面からの入れ替えのみで完了し、アプリの改修は発生しない。**
仮画像は `is_placeholder` で抽出できるため、「実写真がまだの施設一覧」を
管理画面に常時表示し、入稿の進捗を可視化する。

## 8. アプリへの配信方式

施設 3,000 件でもテキストデータは数 MB に収まるため、**都度 API を叩かず、
カタログ全体をスナップショットとして配信**する。

```
管理画面で「公開」
   → catalog_snapshots に version を採番
   → JSON を生成して CDN へ配置
   → アプリは起動時に version を比較し、差分があれば取得
   → 端末内 SQLite に保存
```

この方式の利点:

- **完全なオフライン動作** — 地下の車寄せ、高架下、トンネル内でも案内図と写真が開ける
- **検索が即座に返る** — 端末内で完結するため通信待ちが無い。かな検索・別名検索も可能
- **サーバー費用がほぼ発生しない** — 3,000件規模でも CDN 配信1本で足りる
